# Agent → Ontology → Tool：透明 Aspect 目标架构

状态：用户已确认架构；本文件是设计，不代表各机制已实现。

## 1. 核心决定

主干保持 `Agent → Ontology → Tool`。Aspect 不是第四个业务节点，而是执行连线的横切扩展。Agent 提出业务请求；Ontology 决定业务合法性及状态转换；Tool 实现能力。所有真实业务写入必须经过本体治理，但这个边界必须由工具权限、凭据隔离和服务端入口共同落实，不能仅靠提示词。

Ontology 在部署图上包含业务蓝图与执行运行时，在依赖图上必须分开。业务蓝图/规则不引用 ERP、数据库驱动、宿主会话、溯源存储或 Aspect；运行时解释规则、维护状态和调度执行。数据库 IO 不等于业务蓝图的一部分。

## 2. 透明性的契约

- 业务不调用 trace/emit，不填写溯源字段，不判断 Aspect 是否开启。
- 观察记录由拦截器自动产生，不要求业务主动发送“溯源事件”。
- 执行身份、请求关联、场景等元数据留在可信调用上下文，不混进业务参数。
- 观察型 Aspect 不修改工具输入、输出、业务规则或状态。
- 控制型 Aspect 可以改变调用的调度和可用性，但必须遵守能力契约，不得虚构成功或改变业务规则。
- 管理员应能查看安装的 Aspect、切入点、依赖、版本和策略；透明不等于不可观测。
- 内部执行观测可以透明织入运行时读取/提交边界，无需业务配合。观察点的范围决定溯源粒度；输入输出拦截本身不证明任意内部计算的逐字段血缘。

## 3. 执行连线

执行连线由统一执行织入器实现，承担能力绑定、Aspect 编排、工具结果归一化。绑定属于实例配置，不属于业务模型。

每个业务能力有明确的输入/输出/副作用契约；Tool 实现必须符合契约。端点、认证、协议、参数编码及供应商元数据由适配器处理。相同名称不等于兼容实现。

Agent 不直接获得内部织入器的原始 Tool 调用入口。第一阶段的织入器模块只是内部基础设施，不是 Agent SDK 或公开可调用 API。

## 4. 两级执行作用域

| 作用域 | 职责 |
|---|---|
| 逻辑业务执行 | 请求身份、业务执行标识、权限、幂等、恢复、整体证据 |
| 工具尝试 | 超时、限流、熔断、单次耗时、单次错误与回执 |

多次尝试保持同一个逻辑执行标识，但有不同尝试标识。调用上下文必须在并发、异步与跨进程时正确传播，不使用共享可变全局变量。身份从已认证的运行时上下文获得，不能相信 Agent 自填的 role 字段。

Aspect 的顺序按显式依赖/冲突规则验证。权限不能被缓存绕过；缓存按实例/权限范围/版本隔离；重试服从幂等和结果核实策略；观察记录覆盖拒绝、失败和成功。第一阶段只支持观察型 Aspect，不提前提供可任意改变执行的 around 钩子。

## 5. 三份账与可靠执行

业务状态库回答“什么业务事实成立”；执行账本回答“请求执行到哪一步、如何恢复”；证据库回答“事实和结果从哪里来、依据是什么”。逻辑分离不强制物理分库；初期可用同一 SQLite 的不同基础设施存储模块，以获得本地事务一致性。

正式外部副作用流程：验证业务规则/审批/版本 → 本地事务持久化执行意图及必要业务状态 → 事务提交 → 外部工具调用 → 持久化可核实回执 → 经本体规则确认后续业务状态。不得跨网络长时间占有数据库事务。

“请求发出”不是“业务完成”；超时可能意味着执行结果未知。支持稳定幂等键、结果查询或补偿的 Tool 才能提供相应恢复保证。系统不得对不具备这些能力的 Tool 宣称恰好一次。回滚本地对象也不等于撤销外部副作用。

观察型 Aspect 的失败策略应明确区分可选遥测与强制证据。可选遥测失败不能把成功业务包装成失败；强制证据则需纳入可靠持久化/提交协议，不能在外部操作已成功后简单抛错并让上游重试。

## 6. 溯源的边界

来源由接入 Tool 适配器提供，读写对象版本由运行时自动观察，溯源 Aspect 关联这些事实。业务批次/订单/退款等领域溯源关系仍保留在业务本体。

第一版承诺调用关联、来源关联、对象版本依赖，不承诺任意函数的逐字段精确推导。证据中的版本引用应能定位历史事实，不能只指向会被覆盖的当前行。溯源记录不是免费的历史快照。

证据不默认保存敏感原始请求/响应；访问控制、脱敏、保留期与删除策略适用于证据库。摘要/哈希也不是匿名化保证。

## 7. 沙盘与替换

正式与沙盘复用规则和能力契约，但沙盘默认绑定模拟实现或受限只读实现。Fork 不继承真实写入能力。MCTS 分支的执行与证据隔离，搜索轨迹按需保留，不写入正式业务事实历史。

更换 Tool 实现可以是基础设施行为；改变工单承接人、业务责任人等必须经过本体动作，不得在 Aspect 内偷偷执行。

## 8. 分阶段落地

1. **执行边界基础**：独立内部模块，实例级能力绑定、不可变调用上下文、透明观察型 Aspect；使用受控假工具验证契约。不修改现有业务模型或发布新 Agent 原始工具入口。
2. **一条真实治理路径接入**：选现有一个外围适配调用路径接入织入器，业务动作与参数保持不变；替换词汇黑名单为分层依赖/能力边界检查。此阶段才讨论与现有 Runtime 的接缝。
3. **可靠执行与证据**：实现持久化执行意图、恢复、回执关联及来源/版本证据；以故障注入验证，而非普通 happy-path 测试。
4. **受约束的控制型 Aspect**：按能力逐项加入幂等、重试、熔断、缓存，并验证组合与副作用隔离。

验收核心：业务不感知 Aspect；更换实现不改业务定义；观察型扩展不改业务计算；身份不可伪造；重试不盲目制造重复副作用；崩溃可恢复或明确呈现未知状态；沙盘不触发真实写入；证据不绕过权限。
